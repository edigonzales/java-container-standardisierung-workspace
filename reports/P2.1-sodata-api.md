## CI und Veröffentlichung

`pull_request` führt den bestehenden Gradle-Build, den geladenen amd64-Smoke unter `1000830000:0` mit Read-only RootFS sowie den gemeinsamen amd64/arm64-Build aus. Der Smoke prüft Readiness und die drei XML-Routen mit dem bestehenden Fixture. QEMU registriert arm64 auf dem amd64-Runner. Die Actions verwenden unterstützte Node-24-Majors. Der alte Verweis auf den fehlenden `meta`-Schritt entfällt. Docker-Hub-Secrets werden direkt im geschützten Login-Schritt referenziert. PRs überspringen beide Logins und bauen ohne Push. Die minimale Build-Provenance bleibt erhalten. PR-Läufe zählen bei `github.run_number` mit, weshalb die Release-Versionen Lücken aufweisen können. [Workflow-Änderungen](https://github.com/sogis/sodata-api/pull/4/files) · [Review](P2.1-review.md)

Ein späterer Merge nach `main` oder ein manueller Workflow-Start auf `main` kann Docker Hub und GHCR mit den Tags `latest`, `0`, `0.0` und `0.0.<run_number>` aktualisieren. Im Pilot wurde kein Kandidatenimage publiziert. `latest` zeigte auf beiden Registries weiterhin auf denselben bisherigen Digest. Die Abnahme kann vor dem Merge aus einer freigegebenen Test-Registry erfolgen.

Der PR-Lauf für `d5450e23d6219a69114cd56cd693731a5b047555` war erfolgreich. Gradle, amd64-Smoke und gemeinsamer amd64/arm64-Build waren grün. Beide Registry-Logins wurden übersprungen. ## Manuelle OpenShift-Abnahme

1. Den geprüften Commit aus dem Anwendungs-PR in einem Checkout namens `sodata-api` auschecken. Mit Temurin 17 `./gradlew clean build` ausführen und den SHA-256 des ausführbaren JARs zu diesem Kandidaten festhalten. Mit vorhandener Publish-Berechtigung `TEST_REPO` auf ein dediziertes Test-Repository setzen. Den SHA-Tag nur verwenden, wenn er dort frei ist.

   ```bash
   test -n "${TEST_REPO:?Test-Repository setzen}"
   tag="$TEST_REPO:p21-$(git rev-parse HEAD)"
   shasum -a 256 build/libs/sodata-*-exec.jar
   docker buildx build --platform linux/amd64,linux/arm64 -f Dockerfile.jvm -t "$tag" --push .
   docker buildx imagetools inspect "$tag"
   ```

2. `IMAGE` auf das Test-Repository mit dem ermittelten **Index-Digest** setzen und `NS` auf ein freigegebenes nicht produktives Projekt. Vom App-Checkout aus einen separaten Test-Deployment mit Fixture und schreibgeschütztem ConfigMap-Mount einrichten. Dem Cluster ggf. den vorhandenen Pull-Zugriff auf die Test-Registry geben. Bei abweichender Cluster-Konfiguration die geltenden Ressourcenlimits, Sicherheitsvorgaben und Start-Overrides im Test nachvollziehen.

   ```bash
   test -n "${NS:?Testprojekt setzen}" && test -n "${IMAGE:?Image mit Digest setzen}"
   app=sodata-api-p21
   oc -n "$NS" create configmap "$app" --from-file=datasearch.xml=src/test/resources/datasearch.xml
   oc -n "$NS" create deployment "$app" --image="$IMAGE" --replicas=0
   oc -n "$NS" set volume deploy/"$app" --add --name=config --type=configmap \
     --configmap-name="$app" --mount-path=/config --read-only
   oc -n "$NS" set probe deploy/"$app" --readiness --get-url=http://:8080/actuator/health/readiness
   oc -n "$NS" set probe deploy/"$app" --liveness --get-url=http://:8080/actuator/health/liveness \
     --initial-delay-seconds=30
   oc -n "$NS" scale deploy/"$app" --replicas=1
   oc -n "$NS" rollout status deploy/"$app" --timeout=120s
   ```

3. SCC, Image-ID, effektive UID/GID und Zugriffe prüfen. Bei einem schreibgeschützten RootFS braucht `/tmp` ein beschreibbares `emptyDir`. Bei gesetztem `ILIDATA_DIR` muss auch dieses Mount-Ziel beschreibbar sein.

   ```bash
   pod=$(oc -n "$NS" get pods -l "app=$app" -o jsonpath='{.items[0].metadata.name}')
   oc -n "$NS" get pod "$pod" -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}{.status.containerStatuses[0].imageID}{"\n"}'
   oc -n "$NS" exec "$pod" -- sh -ec 'id; test "$(id -u)" -ne 0; test -r application.jar;
     test ! -w application.jar; test -r /config/datasearch.xml;
     check=$(mktemp /tmp/p21.XXXXXX); rm "$check"; test -s "${ILIDATA_DIR:-/tmp}/ilidata.xml"'
   oc -n "$NS" port-forward deploy/"$app" 18080:8080
   ```

   In einem zweiten Terminal Health prüfen und die XML-Inhalte mit dem Fixture vergleichen. Im Testprojekt zusätzlich einen repräsentativen Download über die dort eingesetzte HTTPS-/CA-Konfiguration abrufen.

   ```bash
   for endpoint in actuator/health/readiness actuator/health/liveness ilisite.xml ilimodels.xml ilidata.xml; do
     curl -fsS "http://127.0.0.1:18080/$endpoint" || break
   done
   ```

4. `oc -n "$NS" logs "$pod"`, `oc -n "$NS" describe pod "$pod"` und, falls Metriken bereitstehen, `oc -n "$NS" adm top pod "$pod"` prüfen. Auf Neustarts, Temp-/Mount-Fehler, Heap und OOM achten. Bei einem Rollout die Terminierung mit der geltenden Grace Period und laufenden Anfragen prüfen.

5. Für einen Rollback den vor dem Rollout in der Zielumgebung erfassten Anwendungsimage-Digest verwenden. Der beobachtete bisherige Multiarch-Index für Docker Hub und GHCR war `sha256:687e80267734aa148e32ffd25fc06a8150f7c1870ed90222651c52bcb225f43d`. Für das separate Test-Deployment mit dem entsprechenden Docker-Hub-Stand:

   ```bash
   oc -n "$NS" set image deploy/"$app" "$app=docker.io/sogis/sodata-api@sha256:687e80267734aa148e32ffd25fc06a8150f7c1870ed90222651c52bcb225f43d"
   oc -n "$NS" rollout status deploy/"$app" --timeout=120s
   ```

## Für die nächsten JVM-Migrationen

Ein einziges JAR bauen und die Hashes in den Vergleichsimages prüfen. Exec-CMD erhält bei diesem Dienst den vollständig überschreibbaren Startbefehl und die 80-%-Heap-Option. Neben den Standardpfaden auch dokumentierte Konfigurations-Overrides und frisch initialisierte Volumes testen. Die Freigabe des konkreten Kandidaten im Cluster umfasst die tatsächlichen Start-Overrides, TLS, Storage-Rechte, Ressourcen und Terminierung unter Last.
